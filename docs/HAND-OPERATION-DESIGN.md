# 手牌操作设计：从「动作卡列表」到「对象—动词—应答」

> 审查基线：`main`（2026-11）。代码引用以符号名为准，行号仅用于定位。
> 性质：**设计审查与方案，不含实现**。本文回答三个问题：
> 1. 当前项目为什么把「手牌」做成了「合法动作列表」；
> 2. 常见桌游/棋牌实际上如何划分手牌与操作；
> 3. 一个可落地的、详细到手牌分区与数据契约的设计是什么。

---

## 0. 结论先行

1. **手牌不是「所有能做的事」的卡片列表**。手牌是玩家私有、可持有、可被规则移动/弃置/交易/计数的**实体集合**；动作是动词，动词应该出现在它的作用点上。
2. 用户提出的「实体牌 / 抽象行为牌」二分方向是对的，但**抽象行为牌不应再作为手牌的一个分区**。抽象行为要按来源继续拆成：回合指令、对象动词、交易/数值、应答/决策。它们各自有固定的家。
3. 当前实现的根因不是「分组不够细」或「分页不够好」，而是数据模型：`snapshot.actions` 是**合法动作表**，`buildActionsView` 把它映射成 `UiAction`，`CardHand` 再把每一张 `UiAction` 渲染成手牌。手牌数量因此与合法动作数同阶，而不是与手牌上限同阶。
4. 推荐模型：**三层六面**。
   - 对象层：手牌、装备/持久区、桌面/市场；
   - 动词层：回合指令轨、情境动词条、交易/数值面板；
   - 应答层：应答/决策托盘。
   外加资源/信息 HUD。手牌只放对象，动词不进场。
5. 量化目标：无论引擎给出 5 条还是 500 条合法动作，**屏幕上可操作项**应有硬预算：手牌一页 7–9 张、指令轨 ≤ 5、情境动词 ≤ 6、应答选项 ≤ 4。可见动作数不再随合法动作数线性增长。
6. 竞技性：默认**意图优先**，不把合法动作全量摊开；「显示所有合法操作」只作为教练/调试/可访问性模式，联机竞技默认关闭。玩家自己推导合法动作，是棋牌乐趣的一部分。

## 2. 当前实现审查

### 2.1 真实链路

~~~
UniversalGameEngine.legalActions(actor)        // 合法动作，数量 N
        ↓
UniversalSession.rebuild()
  acting.flatMap(pid => getLegalActions(pid))  // 合并行动者
        ↓
buildActionsView(state, legal, ...)            // 分组 / 目标塌缩 / 生成 UiAction
        ↓
snapshot.actions: UiAction[]                   // 数量 M，仍是动作表
        ↓
BoardGameHUD.renderActionHand(snapshot)
  - 按 group 排序：card → equip → skill → command
  - 把 zone_hand_{viewer} 中没有被 action 占用的牌追加为 held
        ↓
CardHand.sync(items)                           // 按 action.id 做 DOM key
  - 分页 4–9 张
  - 弧形排布 / 拖拽 / 回弹
        ↓
DOM 手牌
~~~

关键事实：

- `buildActionsView` 对每一条未被 boardGroup 吸收、未被目标塌缩合并的动作执行一次 `bound.push`（`packages/app/src/session.ts:1792` 附近），并生成 `id: 'a' + bound.length`（同文件 1794–1795）。**卡 id 是序号，不是实体 id。**
- `snapshot.actions` 的契约是 `UiAction[]`，不是 `HandCard[]`；它回答的是「现在能做什么」，不是「我手里有什么」。
- `renderActionHand` 把 `snapshot.actions` 全量映射成卡，再按 `GROUP_ORDER` 排序（`apps/web/src/ui/hud.ts:4210` 附近）。分组只改变顺序和颜色，不改变「每张卡是一个合法动作」这一事实。
- held 卡（德州底牌、山屋道具）是在动作卡之后追加的，来源是 `zone_hand_{viewer}`，最多 12 张，并且**只追加没有被动作卡占用的实体**（同文件 4221–4241）。这意味着同一张实体牌会在「动作卡」与「展示卡」两种身份之间切换。

### 2.2 现有分区到底分的是什么

当前 `UiActionGroup` 的定义在 `packages/app/src/contracts.ts:78–85`：

| 现有 group | 推导方式 | 典型内容 | 实际对象 | 问题 |
| --- | --- | --- | --- | --- |
| `card` | 动作带 `entityId`，且实体在 HAND/EQUIP，或任意带 entityId 的动作 | 三国杀【杀】、山屋道具、璀璨宝石市场卡 | 不一定是手牌：市场卡、房间物品、装备区牌都会被归进来 | 「card」不是「手牌」，是「动作带了一个实体」 |
| `equip` | `action.type === 'EQUIP_CARD'` | 装备动作 | 动作，不是装备后的实体 | 装备实体装备后反而离开这个组 |
| `skill` | `action.type === 'USE_SKILL'` | 武将技能、物品技能 | 能力，不是牌 | 技能可能消耗手牌（entityId），被当成「技能卡」 |
| `command` | 其余全部 | 结束回合、掷骰、过牌、跟注、加注、建造、交易、响应、选项 | 异质的动作集合 | 一个组里混了六种完全不同的操作域 |
| held（非 group） | `display:` 前缀，来自手牌区 | 德州底牌、山屋物品 | entity | 只在「没有对应动作」时出现，身份不稳定 |

这张表说明：**当前分组按「动作长什么样」分，而不是按「对象在哪里、动词属于谁」分。** 所以即使把 group 拆成十种，只要仍然把每条合法动作渲染成卡，问题不会消失。

### 2.3 问题清单

#### H1 · 手牌 = 合法动作列表（根因）

`snapshot.actions` 是引擎合法动作的投影。`buildActionsView` 的目标塌缩减少了「同一张杀 × N 个目标」的重复，但没有改变「每个可执行动作一条记录」的本质。于是：

- 手牌数量由「当前回合有多少合法动作」决定；
- 动作越多，卡越多；分页只是把爆炸藏到第二页；
- 玩家看到的是「规则允许的所有选项」，而不是「我持有的牌」。

#### H2 · group 是动作形态，不是对象位置

`groupOf` 的注释说「实体在手牌/装备区 → 牌；技能 → 技能；装备动作 → 装；其余 → 命令」，但实际代码里 `if (action.entityId) return 'card'`，所以市场卡、房间物品、装备区牌都会被归为 `card`。这不是「手牌分区」，是「动作是否带实体」的二分。

#### H3 · command 是万能垃圾桶

`command` 同时承载：

- 回合流：结束回合、过牌、准备、开下一手；
- 随机/系统：掷骰、摸牌；
- 经济：建造、购买、交易；
- 下注：弃牌、过牌、跟注、加注、全下；
- 响应：出闪、出桃、无懈、放弃；
- 决策：选择一项、分配伤害、弃半牌。

这些操作的生命周期、位置、确认策略、计时策略完全不同，却被放在同一个组里按引擎顺序排列。玩家无法形成稳定的空间记忆。

#### H4 · held 卡是二等公民，身份会跳变

`display:` 前缀把「只展示的持有牌」和「可执行的动作卡」分成两套 id。一个实体牌在不可用时是 `display:{entityId}`，可用时变成 `aN`。这会导致：

- DOM 节点重建、动画重置；
- 玩家刚看到的牌「换了一个身份」；
- `CardHand` 的按 id 复用失效；
- 同一张牌无法同时拥有「查看 / 打出 / 弃置 / 交易」多个动词。

#### H5 · 分页把命令和真手牌混在一起

`CardHand.pageSizeForWidth` 按宽度把每页定为 4–9 张，分页对象是**全部 item**。当手牌 5 张、命令 8 条时，玩家可能翻到第二页才看到自己的手牌。分页本身不是问题，「分页的单位错了」才是问题。

#### H6 · 动作 id 是序号，不是稳定身份

`id: 'a' + bound.length` 意味着动作顺序一变，id 就变。`CardHand.sync` 用 id 做 key，于是快照刷新时：

- 同一张牌可能被当成新卡；
- 正在拖拽/悬停的卡可能被替换；
- 动画状态、焦点、滚动位置丢失；
- 探针里的「节点复用」很难稳定。

手牌卡应该用 `entityId` 做 key；指令应该用 `actionType + slot` 做 key；应答应该用 `promptId` 做 key。

#### H7 · 全量枚举削弱竞技性

棋牌的核心乐趣之一是「从局面推导合法行动」。把全部合法动作摊成手牌，相当于给玩家一个实时规则求解器：

- 玩家不需要记住牌型、距离、费用、响应规则；
- 新手和老手的差距被 UI 抹平；
- 在隐藏信息游戏里，动作列表还可能泄露「哪些目标合法」这类本应由玩家推理的信息；
- 观战/直播时，手牌动作列表会把玩家的可选范围公开。

这不是说「不能有帮助」，而是说**帮助应该是可选的、克制的、分层的**，不能成为默认手牌。

#### H8 · 布局抖动与空间记忆缺失

动作数量随回合变化，手牌宽度、分页、排序随之变化。玩家刚记住「结束回合在右下角」，下一回合它可能被挤到第二页。竞技玩家需要的是**固定槽位**：结束回合永远在同一位置，弃牌/过牌/跟注/加注永远同一顺序。

#### H9 · 游戏专用文案在通用层

`packages/app/src/actionText.ts` 的 `describeActionZh` 是一个按 `action.type` 展开的巨型 switch，包含「捕捉宝可梦」「破译神圣符文」「月相压制仪式」等游戏词汇。这违反 `AGENTS.md` §3.1 的「能力优先于身份」：通用层不应该知道某款游戏的术语。它也让「动作分类」被游戏文案绑死，新增游戏必须改通用层。正确做法是游戏在 `GamePresentationHints` 里声明 `actionView`，通用层只给中性默认值。

#### H10 · 没有动作预算，只有分页

当前没有「手牌最多几张、指令最多几条、应答最多几项」的硬预算。分页是事后补丁，不是设计约束。结果是：动作多就多分页，分页多了玩家就翻不到；性能上也要为所有动作建模型、做排序、算签名。

#### H11 · 响应/决策没有独立通道

三国杀的【闪】【桃】【无懈】、麻将的吃/碰/杠/胡、卡坦的弃半牌、Dune 的秘密战斗转盘，都是**游戏在问你问题**。它们现在和主动出牌共用 `snapshot.actions`，于是响应选项也变成手牌卡。响应是时间敏感、只能选合法项、通常有倒计时和「放弃」的交互，应该走独立托盘，而不是手牌。

#### H12 · 多套入口仍在

`?unified-hand` 是特性开关（`apps/web/src/ui/hud.ts:2095`），旧 dock 扇形、`#hand-slot`、3D 只读手牌仍然存在。多套入口意味着同一份 `snapshot.actions` 被多个组件以不同方式解释，分类逻辑无法收敛。设计落地时必须明确唯一入口与退役顺序。

### 2.4 量化：动作数如何变成手牌数

以代码结构说明，不依赖精确局面：

| 游戏 | 合法动作的生成方式 | 当前手牌里会出现什么 | 真正的手牌实体 |
| --- | --- | --- | --- |
| 德州扑克 | 每个下注选项一条（FOLD/CHECK/CALL/RAISE/ALL_IN），加准备/开手 | 底牌 + 5–7 张命令卡 | 2 张底牌 |
| 卡坦岛 | 每个可建顶点/边一条，加上掷骰、买卡、银行交易、玩家交易、结束回合 | 建造/交易/结束回合等命令卡；有发展卡时再加发展卡 | 发展卡（若有） |
| 三国杀 | 每张手牌 × 每个合法目标；每个技能 × 每张牌 × 每个目标；响应窗口再生成闪/桃/无懈 | 手牌 + 技能卡 + 响应卡 + 结束回合 | 手牌（杀/闪/桃/锦囊/装备） |
| 山屋惊魂 | 移动、探索、攻击、使用物品、房间特性、结束回合等几十种动作 | 物品 + 大量命令/情境卡 | 物品/预兆 |
| 璀璨宝石 | 拿币组合、买卡、保留卡、进化 | 全部是命令卡 | 保留卡（若有） |
| 麻将 | 打牌、吃/碰/杠/胡、战斗转盘 | 手牌 + 响应选项 + 系统命令 | 手牌 |

结论：**M 与 N 同阶**。分页把每页压到 4–9 张，但没有改变「总卡数 = 合法动作数」这一事实。真正要改的是「哪些东西有资格成为手牌卡」。

## 3. 常见桌游/棋牌的操作设计调研

### 3.1 横向对照

| 游戏 | 手牌是什么 | 动作在哪里 | 响应怎么做 | 可借鉴的结论 |
| --- | --- | --- | --- | --- |
| 斗地主 | 17–20 张实体牌，牌本身是唯一资源 | 选牌后点「出牌 / 不出」；叫地主是独立按钮 | 跟牌/不出是按钮，不是手牌卡 | 手牌只放牌；「提示」是可选辅助，不是全量动作列表 |
| 三国杀 | 手牌（杀/闪/桃/锦囊/装备） | 选牌 → 选目标；技能是武将/装备上的独立能力按钮；装备进装备区 | 【闪】【桃】【无懈】在响应窗口弹出，只列合法响应 + 放弃 | 技能不是手牌；响应是 prompt；装备区独立 |
| 炉石传说 | 手牌（随从/法术/武器） | 拖牌到棋盘/目标；英雄技能是独立按钮；结束回合固定在右下 | 发现/抉择/对手回合的奥秘是弹出式选择 | 固定结束回合；手牌是对象；费用/法力是资源条 |
| 万智牌 | 手牌（地/咒语） | 手牌打出；战场永久物；优先权/堆叠是独立控制 | 优先权传递、响应是 prompt；「pass」是固定按钮 | 堆叠/优先权是应答层，不是手牌 |
| 德州扑克 | 底牌（只读展示） | 下注控制台：弃牌/过牌/跟注/加注/全下 + 数额滑块 | 摊牌/准备是结算提示 | 下注是固定顺序的控制台；底牌不是动作卡 |
| 卡坦岛 | 资源是计数，发展卡是实体牌 | 建造面板（费用表）+ 棋盘高亮；交易对话框；掷骰/结束回合固定 | 弃半牌/交易接受是决策窗口 | 经济动作是面板，不是手牌；资源是计数 |
| 璀璨宝石 | 保留卡是实体牌；宝石是计数 | 市场卡可点；拿币/购买/保留是市场操作；支付是数值面板 | 无典型响应；进化是选择 | 市场卡是桌面对象，不是手牌；代币是资源条 |
| 山屋惊魂 | 物品/预兆是实体牌 | 移动/探索/攻击在棋盘；使用物品在物品卡上；结束回合固定 | 事件/预兆/检定是 prompt；伤害分配是选择 | 物品卡可以带「使用」动词，但动词属于物品，不是手牌列表 |
| 麻将 | 手牌牌张 | 点牌打出；吃/碰/杠/胡是响应按钮 | 只列当前可声明项 + 过 | 响应按钮是棋牌最经典的 prompt 范式 |
| UNO | 手牌牌张 | 点牌打出；摸牌/过牌是按钮 | 抽牌/跳过/颜色选择是 prompt | 手牌 + 两个固定按钮即可 |
| 幽港迷城 | **行动牌是实体资源**（每回合选两张） | 选两张行动牌 → 选先攻/移动/攻击；技能在牌面 | 长休/短休、怪物行动是回合流程 | 反例：当游戏的核心资源就是行动牌时，行动牌当然是手牌实体 |
| BGA 通用规范 | 私有资源放面板 | 中央棋盘承担共享动作；不要用动作栏替代棋盘组件 | 选择目标时持续高亮合法项、显示 n/N、显式取消 | 主操作区不可遮挡；失败必须说明原因；破坏性动作限时确认 |

### 3.2 五条共识

1. **手牌是对象，动词是控制。** 斗地主、炉石、万智牌、UNO 的手牌都是「可以被规则移动的牌」；「出牌/过牌」是控制，不是牌。
2. **动词出现在它的作用点。** 卡牌动词在卡上/卡旁；棋盘动词在棋盘热点；经济动词在费用面板；回合动词在固定轨；响应动词在弹窗。
3. **固定空间记忆 + 有界选项。** 结束回合、弃牌/过牌/跟注/加注、pass 都在固定位置；可见选项数量有上限，不随合法动作数增长。
4. **响应是 prompt，不是手牌。** 三国杀【闪】、麻将吃碰杠胡、万智牌优先权、UNO 抽牌，都是「游戏问你」，只列合法项 + 放弃/确认。
5. **全量合法动作是辅助，不是默认。** 斗地主的「提示」、BGA 的合法项高亮、调试器的动作面板，都是可选辅助；默认界面让玩家自己推导。

### 3.3 反例与边界：什么时候「行动牌」真的是手牌

幽港迷城、精灵岛、魔法骑士这类游戏，**行动牌本身就是核心资源**：有牌名、有牌堆、有手牌上限、会被弃置/休整/洗回。它们当然应该出现在手牌区。

判定标准不是「抽象还是具体」，而是**有没有游戏状态中的持久身份**：

- 能被移动、弃置、偷走、交易、洗回、计数、展示 → 实体牌；
- 只是「当前合法动作的一条投影」→ 命令/动词，不是牌。

这条标准可以总结成一句：**「这张牌离开 UI 之后，游戏状态里还存在吗？」** 存在就是实体，不存在就是命令。

### 3.4 三种候选方案对比

| 方案 | 语义 | 动作膨胀 | 竞技性 | 实现成本 | 判断 |
| --- | --- | --- | --- | --- | --- |
| A. 全动作卡（现状） | 手牌 = 合法动作列表 | 随 N 线性增长，分页掩盖 | 差，等于求解器 | 已有 | 否决 |
| B. 手牌分区（实体区 + 行为区） | 手牌内再分「实体牌/行为牌」 | 行为区仍随 N 增长，除非行为区是固定指令 | 中，仍偏向枚举 | 中 | 可作为过渡皮肤，不作为最终模型 |
| C. 对象—动词—应答分层（推荐） | 手牌只放对象；动词按作用点分层 | 可见项有硬预算，与 N 解耦 | 好，默认意图优先 | 中高，但可分阶段 | **推荐** |

> 如果产品坚持「手牌分区」的视觉隐喻，方案 B 可以保留，但必须加三条硬约束：行为区**固定槽位、最多 5 条、不分页、不与实体牌混排**。否则它只是把方案 A 换了个颜色。

## 4. 设计原则

### P1 · 对象与动词分离

**对象**是游戏状态里存在的东西：牌、装备、物品、棋子、房间、市场卡。
**动词**是玩家对对象/局面施加的操作：打出、装备、使用、弃置、交易、建造、跟注、结束回合。

UI 的基本单位因此不是「一张动作卡」，而是：

~~~
对象（Object） --动词（Verb）--> 目标（Target） --参数（Payload）--> 引擎
~~~

手牌只负责「对象」；动词由对象、棋盘、回合、应答各自承载。

### P2 · 手牌由规则决定，不由合法动作决定

手牌数量应该等于 zone_hand_{viewer} 里的实体数量（受规则手牌上限约束），而不是 snapshot.actions.length。一局斗地主的手牌可以是 17 张，但「能出的牌型」可能有几十种；后者不应该变成 17+ 张卡。

### P3 · 动词归属作用点

| 动词的作用点 | 动词的家 |
| --- | --- |
| 一张手牌 | 卡旁/卡上（情境动词条） |
| 一个棋盘位置/边/房间 | 棋盘热点、落点高亮、径向选择 |
| 一个市场/建造/交易过程 | 交易面板或费用面板 |
| 回合本身 | 回合指令轨（固定槽位） |
| 游戏在问玩家 | 应答托盘 |
| 资源/分数/状态 | 资源条/信息 HUD（只读） |

同一个「打出」动词，在不同作用点的表现不同：手牌是拖拽/点选，棋盘是点击热点，市场是购买按钮。不要用一个「动作卡列表」同时承担所有作用点。

### P4 · 固定空间记忆

高频动作必须有固定位置和固定顺序：

- 结束回合：指令轨最右，永远同一位置；
- 弃牌 / 过牌 / 跟注 / 加注 / 全下：下注控制台从左到右固定顺序；
- 确认在右、取消在左；
- 应答托盘的「放弃」固定在最后一项；
- 手牌排序默认稳定（类型 → 费用 → 名称），玩家手动排序后持久化。

位置固定比「智能排序」更重要。智能排序会让玩家每次都要重新找按钮。

### P5 · 意图优先，解法后置

默认界面只呈现「我有什么」和「我现在能对什么施加动词」，不主动列出「所有合法动作」。玩家先产生意图（选牌/选目标/选建造），系统再高亮合法目标、给出参数。

把「所有合法动作」作为可选辅助：

- 新手模式：提示一个建议 + 解释；
- 教练模式：可展开合法动作清单；
- 调试模式：全量动作表；
- 联机竞技：默认关闭。

### P6 · 单一身份

一张实体牌从抽到、到手、可打出、打出、进弃牌堆，应该始终是同一个 entityId、同一个 DOM key、同一套卡面。可打出/不可打出只是卡的状态，不是换一张卡。

指令也一样：end-turn 永远是同一个 command key；不能因为顺序变化变成另一条。

### P7 · 预算与溢出

每个面都有硬预算，溢出有明确的降级路径：

| 面 | 预算 | 溢出策略 |
| --- | --- | --- |
| 手牌 | 每页 7–9 张 | 按**牌数**翻页，不按动作数 |
| 指令轨 | 5 条 | 第 5 条为「更多」，其余进菜单 |
| 情境动词 | 6 条 | 次要动词进「更多」子菜单 |
| 应答选项 | 4 条 | 列表滚动，但首屏不超过 4 条 |
| 交易/数值 | 1 个面板 | 一次只开一个，确认后关闭 |
| 资源条 | 8 个计数 | 折叠为「资源详情」 |

预算不是「建议」，是探针断言。超过预算就说明分类错了，而不是「再加一页」。

### P8 · 可访问性等价路径

视觉分层不能剥夺键盘/读屏用户的操作能力。每个面都要有线性等价物：

- 手牌：role=listbox + roving tabindex，←/→ 切换，Enter 查看/选择；
- 指令轨：role=toolbar，固定顺序，数字快捷键；
- 情境菜单：role=menu，方向键 + Enter；
- 应答托盘：role=alertdialog，1–4 选项，Esc 仅当允许放弃；
- 全量动作：Ctrl+K 命令面板，线性列出当前可用动作（也是教练/调试模式）。

### P9 · 引擎裁决，UI 不造规则

UI 只收集「对象 + 动词 + 目标 + 参数」，合法性一律交给 dispatch。候选目标来自 engine.getSelectionCandidates；非法目标在 UI 层可以预置灰，但不能代替引擎判定。失败必须回显 result.error 的人话原因。

### P10 · 复用既有基础设施

- 浮层仍走 OverlayArbiter（peek < pinned < modal），应答托盘/数值面板不得另起通道；
- 手牌物理仍用 ui/cardHand（弧形、弹簧、拖拽、回弹）；
- 键位表仍用 ui/keymap.ts；
- 探针沿用 probe:* / test:ui / verify:all 口径；
- 不引入新框架，不把状态写进 DOM。

## 5. 总体模型：三层六面

### 5.1 三层

| 层 | 回答的问题 | 主要内容 | 不应该出现的东西 |
| --- | --- | --- | --- |
| **对象层** | 我拥有/场上有什么？ | 手牌、装备、持久牌、桌面牌、市场卡、资源计数 | 合法动作列表 |
| **动词层** | 我能对它做什么？ | 回合指令、情境动词、建造/交易/下注/支付 | 实体牌（除了作为动词的视觉锚点） |
| **应答层** | 游戏在问我什么？ | 响应窗口、强制选择、弃牌、秘密决策、确认 | 主动出牌、全局命令 |

### 5.2 六个操作面

| 面 | 装什么 | 生命周期 | 预算 | 位置 | 交互 | 典型 |
| --- | --- | --- | --- | --- | --- | --- |
| **Hand 手牌** | 私有实体牌（HAND 区） | 持久到牌离开手牌 | 规则手牌上限；每页 7–9 | 底部主区 | 点选/拖出/右键菜单 | 斗地主、三国杀、炉石 |
| **Equip/Tableau 装备/持久** | 装备、已购卡、保留卡、判定牌、持续效果 | 持久 | 槽位/行 | 手牌上方或右侧 | 点击查看/使用/卸下 | 三国杀装备、山屋物品、璀璨宝石保留 |
| **Turn Rail 回合指令轨** | 回合流/系统动作 | 常驻 | ≤5 | 手牌上方右侧 | 单击；确认策略 | 结束回合、掷骰、准备、开手 |
| **Context 情境动词** | 当前选中对象的动词 | 临时 | ≤6 | 对象旁/底部动作条 | 点选动词 → 选目标 | 打出、装备、弃置、交易、使用 |
| **Transaction 交易/数值** | 建造、交易、下注、支付、分配 | 临时面板 | 1 个 | 侧栏/底部 sheet | 表单 + 滑块 + 确认 | 卡坦建造、德州下注、璀璨支付 |
| **Prompt 应答托盘** | 游戏发起的响应/选择 | 临时，阻塞 | ≤4 选项 | 手牌上方，覆盖指令轨 | 按钮/数字键/倒计时 | 闪、桃、无懈、吃碰杠胡、弃半牌 |

> 另外两个**非操作面**：
> - **Board/Table 桌面**：公共牌、市场、弃牌、建筑、房间；是对象，不是手牌；
> - **Info HUD 信息**：回合、阶段、计时、目标、分数、日志、栈；只读。

├───────────────┬──────────────────────────────────────────┬───────────────┤
│ 角色卡/玩家栏 │            棋盘 / 公共牌桌                 │ 日志/详情面板 │

│  「曹操对你使用【杀】」   [出闪 ×2] [八卦判定] [放弃]        ⏱ 8s        │
├──────────────────────────────────────────────────────────────────────────┤
│ 回合指令轨 Turn Rail（固定槽位，≤5）  [掷骰] [准备] [更多…] [结束回合]   │
├──────────────────────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────────────────────┤

情境动词条不常驻：选中一张牌/一个棋盘对象后，浮在该对象旁；触屏则从底部升起动作 sheet。

### 5.4 预算与「可见动作」公式

当前：

~~~
可见卡数 ≈ |snapshot.actions|      // 与合法动作数同阶
~~~

目标：

~~~
可见可操作项 = 手牌页(≤9) + 指令轨(≤5) + 情境动词(≤6) + 应答选项(≤4)
             ≤ 24
真正可点击的动作 ≤ 5 + 6 + 4 = 15（手牌还要先选牌）
~~~

即使引擎有 500 条合法动作，屏幕上也不超过 24 个可操作项。合法动作的「多」被藏在：

- 手牌内部的牌数（规则决定）；
- 棋盘高亮目标（选中动词后才出现）；
- 交易面板的候选（打开后才出现）；
- 应答托盘的合法项（游戏提问时才出现）。

### 5.5 手牌是可选的

**没有手牌的游戏不应该有手牌区。** 这是当前设计最大的视觉误导：卡坦、璀璨宝石在开局时没有手牌，却因为所有动作都是命令卡而显示一条「手牌」。

新规则：

- zone_hand_{viewer} + zone_equip_{viewer} + zone_tableau_{viewer} 都为空 → 不渲染 Hand 面；
- 只渲染 Turn Rail + Resource Strip + Board；
- 玩家抽到第一张牌时，Hand 面从底部滑出；
- 手牌清空时，Hand 面收缩为一条「无手牌」的窄条，不保留空白大面板。

### 5.6 如果产品坚持「手牌分区」：方案 B 的硬约束

可以保留「手牌区」作为底部复合控件，但内部必须是**语义分区**，不是「动作卡换颜色」：

~~~
┌─ 手牌操作台 ─────────────────────────────────────────────────────────────┐
│  ┌─ 实体牌区（70%）────────────────────┐  ┌─ 指令区（30%，固定槽）────┐  │
│  │  🂡  🂢  🂣  🂤  🂥                  │  │ [掷骰] [更多] [结束回合]  │  │
│  │  可排序 / 可翻页 / 可拖出           │  │ 最多 5 条 / 不分页        │  │
│  └────────────────────────────────────┘  └───────────────────────────┘  │
│  资源条：木3 砖2 羊1 麦0 矿1                                             │
└──────────────────────────────────────────────────────────────────────────┘
~~~

三条硬约束：

1. 指令区只放**回合/系统**动词，不放对象动词、不放经济动作、不放响应；
2. 指令区固定槽位、最多 5 条、不分页、不随合法动作数增长；
3. 实体牌区只放实体，entityId 是唯一 key；可打出/不可打出是状态，不是换卡。

满足这三条，方案 B 可以作为方案 C 的视觉变体；不满足，就退回方案 A。

## 6. 详细分区分类方案

### 6.1 判定树：一个 UI 元素该去哪里

对每一条「玩家可做的事」依次问：

1. **它在游戏状态里有持久身份吗？**
   - 有：能被移动/弃置/偷走/交易/洗回/计数/展示 → **实体牌**。
   - 没有 → 继续。
2. **它是游戏主动问玩家的问题吗？**
   - 是（响应窗口、强制选择、弃牌、秘密决策、确认）→ **应答托盘（Prompt）**。
3. **它是回合本身的操作吗？**
   - 是（结束回合、过牌、准备、开手、掷骰、摸牌）→ **回合指令轨（Turn Rail）**。
4. **它绑定在某个已选对象/棋盘位置上吗？**
   - 是（打出、装备、使用、弃置、交易、建造、移动、攻击、探索）→ **情境动词（Context）**。
5. **它需要金额/费用/支付/分配吗？**
   - 是（下注、加注、建造费用、支付宝石、分配伤害、弃 N 张）→ **交易/数值面板（Transaction/Amount）**。
6. **它是元操作/信息吗？**
   - 是（设置、撤销、回放、日志、分数、计时）→ **顶栏/信息 HUD**。
7. **仍然无法归类？**
   - 放「更多」菜单或调试用命令面板；**不要放回手牌**。

### 6.2 分区总表

| 分区 | 判定 | 典型内容 | 交互 | 生命周期 | 反例（不应放这里） |
| --- | --- | --- | --- | --- | --- |
| **A 手牌实体** | entity.zoneId 是 HAND，且有实体 id | 斗地主手牌；三国杀杀/闪/桃/锦囊/装备；炉石随从/法术；UNO 牌 | 点选/拖出/右键菜单/翻页 | 到离开手牌 | 结束回合、跟注、建造、闪避响应 |
| **B 装备/持久** | zoneId 是 EQUIP / TABLEAU / JUDGE，或持续效果 | 三国杀装备/判定牌；山屋已装备物品；璀璨宝石保留卡/已购卡；炉石武器/奥秘 | 点击查看/使用/卸下 | 持久 | 手牌中的装备牌（装备前在 A，装备后进 B） |
| **C 展示/秘密** | 只对本人可见的底牌/身份/任务 | 德州底牌；身份牌；秘密目标；山屋预兆（若只对本人可见） | 点击查看；不可拖出 | 到公开/弃置 | 可打出的手牌；公共牌 |
| **D 回合指令** | 无实体、无目标、作用于回合 | 结束回合、过牌、准备、开手、掷骰、摸牌 | 单击；禁用要说明原因；确认策略 | 常驻 | 建造、交易、下注、响应 |
| **E 情境动词** | 绑定到选中对象/棋盘位置 | 打出、装备、使用、弃置、交易、建造道路、移动、攻击、探索 | 点动词 → 选目标/参数 | 选中期间 | 全局结束回合、所有对象的动作列表 |
| **F 交易/数值** | 需要金额/费用/支付/分配 | 卡坦建造/银行交易/玩家交易；德州下注；璀璨支付；伤害分配 | 表单 + 滑块 + 快捷档 + 确认 | 面板打开期间 | 单张牌的基础「打出」 |
| **G 应答/决策** | 游戏发起、阻塞、只能选合法项 | 闪/桃/无懈；麻将吃碰杠胡；弃半牌；Dune 战斗转盘；确认 | 按钮/数字键/倒计时/放弃 | 窗口打开期间 | 主动出牌、回合结束 |
| **H 资源/信息** | 计数/状态/日志，不可操作 | HP、法力、宝石、筹码、资源、分数、回合、计时、日志 | 只读；可展开详情 | 常驻 | 任何可执行动作 |
| **I 桌面/市场** | 共享区域里的实体 | 公共牌、市场卡、弃牌堆、建筑、房间、怪物 | 点击查看；选中后走 E | 持久 | 私手牌、命令按钮 |

### 6.3 手牌区内部子分区

手牌区不是一块铁板，内部按**实体所在区域**分四个子区：

#### H1 · 手牌（HAND）

- 来源：zone_hand_{viewer}；
- 卡面：真实卡图 + 名称 + 类型角标；
- 排序：默认 类型 → 费用/点数 → 名称，玩家可拖动改序，偏好持久化；
- 分页：按牌数，每页 7–9 张；页码只属于手牌，不属于指令；
- 卡状态：

| 状态 | 视觉 | 交互 | 说明 |
| --- | --- | --- | --- |
| 普通 | 正常卡面 | 点选查看动词 | 不可用时也保持可查看 |
| 可打出 | 细金边/微光点 | 拖出或选「打出」 | 不要所有可出牌都强发光，避免噪声 |
| 需要目标 | 右上角 ◎ | 选「打出」后高亮目标 | 目标来自引擎候选 |
| 需要数量 | 右上角 # | 选「打出」后开数值面板 | 不在卡上填数字 |
| 费用不足 | 费用图标变红/卡面 45% 灰 | 仍可查看；尝试时说明原因 | 不要直接隐藏 |
| 冷却 | 倒计时角标 | 点击提示剩余秒数 | 复用 cooldownMs |
| 已选中 | 上浮 12px + 外框 | 显示情境动词条 | 单击选中，不是直接执行 |
| 新抽到 | 短暂高亮 400ms | 无 | 只提示「有新牌」 |
| 装备后 | 从 H1 移到 H2 | 点击查看/卸下 | 同一 entityId，不换卡 |

#### H2 · 装备/持久（EQUIP / TABLEAU / JUDGE）

- 横向槽位或小卡排，不参与手牌扇形；
- 点击查看详情，动词条给「使用/卸下/替换」；
- 判定牌/延迟锦囊放在独立小槽，标明结算时机；
- 已购卡/保留卡按类型分组，不挤占手牌翻页。

#### H3 · 展示/秘密（REVEAL）

- 只对本人可见的底牌、身份、任务；
- 卡面朝上给本人，朝下给旁观/对手；
- 不可拖出，不参与「可打出」判断；
- 点击查看，不产生动作；
- 与 H1 的边界：**能打出的牌在 H1；只能看的牌在 H3**。

#### H4 · 状态标记（EFFECTS）

- buff/debuff、持续效果、标记，用 chip 而非卡；
- 点击展开说明；
- 不参与手牌排序与翻页。

### 6.4 回合指令轨（D）

只放「回合本身」的动作，不放对象动词/经济/响应。

| 子类 | 内容 | 例子 | 位置 |
| --- | --- | --- | --- |
| D1 回合流 | 结束回合、过牌、准备、开手、下一手 | END_TURN、PASS、READY、START_HAND | 最右固定 |
| D2 随机/系统 | 掷骰、摸牌、发牌、洗牌 | ROLL_DICE、DRAW | 最左固定 |
| D3 更多 | 低频/危险/元操作 | 投降、让位、设置、调试 | 「更多」菜单 |

规则：

- 最多 5 条；第 5 条是「更多」，其余进菜单；
- 固定槽位：[随机/系统] [准备/开始] [更多] [结束回合]；没有某类就留空，不左右移动其他槽；
- 禁用时显示原因（「还没掷骰」「等待其他玩家」），不是消失；
- 破坏性动作（结束回合但还有未用行动/资源）走 5–8 秒限时确认条，不弹全屏 modal；
- 指令不是卡：形状为 pill/按钮，不能拖拽，不能与手牌混排。

### 6.5 情境动词（E）

| 子类 | 何时出现 | 动词 | 目标/参数 | 例子 |
| --- | --- | --- | --- | --- |
| E1 查看 | 选中任意对象 | 查看 | 无 | 所有卡/房间/玩家 |
| E2 打出/使用 | 选中手牌/装备/物品 | 打出、使用、施放 | 目标/数量/放置 | 炉石拖牌、山屋使用物品 |
| E3 装备/卸下 | 选中装备牌/装备槽 | 装备、替换、卸下 | 槽位 | 三国杀装备 |
| E4 弃置/交易/给予 | 选中手牌/物品 | 弃置、交易、给予 | 玩家/数量 | 山屋交易、卡坦资源 |
| E5 棋盘动作 | 选中棋盘对象/位置 | 建造、移动、攻击、探索、拾取 | 棋盘节点/边/房间 | 卡坦建路、山屋探索 |

关键：

- **技能不是手牌卡**。武将技能放在角色卡/技能条上；需要弃牌时，先选技能，再选牌，而不是把「制衡 · 弃某张牌」做成一张手牌。

- 情境动词条最多 6 条；超过时「查看」固定第一，「更多」固定最后。

### 6.6 交易/数值面板（F）

| 子类 | 触发 | 内容 | 确认 |
| --- | --- | --- | --- |
| F1 建造面板 | 选中「建造」动词/打开建造按钮 | 费用表、可建类型、当前资源、合法位置高亮 | 选类型 → 点棋盘 → 确认 |
| F2 交易面板 | 选中「交易」动词 | 给/要、汇率、对象玩家、可接受性 | 提议/接受/拒绝 |
| F3 下注控制台 | 轮到下注 | 弃牌/过牌/跟注/加注/全下 + 数额滑块 + 底池/跟注额/筹码 | 单击选项；加注需滑块确认 |
| F4 支付/分配面板 | 需要支付/分配/弃 N | 支付组合、伤害分配、弃牌选择、数量 | 确认后 dispatch |

规则：

- 面板一次只开一个；打开时手牌仍可见但不可拖出（避免误操作）；
- 所有数值有 min/max/step，滑块旁有数字输入；
- 快捷档来自游戏声明（marks），通用层只渲染；
- 显示「后果预览」：支付后剩余、加注后筹码、弃牌后手牌数；
- 取消不产生任何状态变更（数值先甩后填的视觉动画不等于 dispatch）。

### 6.7 应答/决策托盘（G）

| 子类 | 触发 | 界面 | 退出 |
| --- | --- | --- | --- |

| G2 强制选择 | 技能/卡牌要求选一项 | 选项按钮；无放弃（除非规则允许） | 选择 |
| G3 弃牌/选 N | 手牌上限、弃半牌 | 展示手牌/候选，计数 n/N，确认 | 选够 + 确认 |
| G4 同时秘密决策 | Dune 战斗转盘、同时选牌 | 隐藏输入、锁定、全部提交后揭示 | 提交 |

规则：

- 托盘出现在手牌上方，**覆盖指令轨**，不覆盖手牌（玩家需要看自己的牌来回应）；
- 只列合法项；非法项不显示或置灰并说明；
- 选项中「放弃/跳过」固定最后；没有放弃时不要假装有；
- 键盘 1–4 选择，Enter 确认，Esc 仅在允许放弃时生效；
- 多个 prompt 排队，显示 1/2；不要叠多个 modal；
- 超时行为由游戏声明（timeoutAction），UI 只显示倒计时；
- 观战者只看到「等待某玩家」，不看到选项。

### 6.8 资源/信息（H）

## 7. 交互状态机与手势

### 7.1 手牌卡的手势

| 手势 | 桌面 | 触屏 | 语义 | 备注 |
| --- | --- | --- | --- | --- |
| 悬停 | 指针停留 150–200ms | 无 | peek 详情 | 走 OverlayArbiter 的 peek，不改变选中 |
| 单击 | 左键单击 | 轻触 | 选中 + 显示情境动词条 | 不直接 dispatch |
| 双击 | 左键双击 | 双击 | 快速打出（仅当只有一个动词且无需目标/数量） | 可在设置里关闭 |
| 拖出 | 按住拖动 | 按住拖动 | 打出；需要目标则弹径向选择器 | 松手在出牌区才生效 |
| 右键 | 右键 | 长按 500ms | 情境菜单（查看/打出/装备/弃置/交易） | 长按不再是「执行」 |
| 方向键 | ←/→ | 无 | 手牌间切换焦点 | 容器有焦点时生效 |
| Enter | Enter | 无 | 等同双击/确认 | 需要目标时打开选择器 |

**关键改变**：长按从「执行」改为「更多」。当前长按执行是一个隐藏手势，误触代价高，且与「长按看详情」的通用习惯冲突。执行收敛到双击/拖出/动词条，长按只负责菜单。

可选设置：

- **休闲模式**：单击简单卡直接打出（少一步）；
- **竞技模式（默认）**：单击只选中，双击/拖出才打出；
- **触屏**：轻触选中，再次轻触已选中的卡打出；长按菜单。

### 7.2 手牌交互状态机

| 状态 | 进入 | 允许 | 退出 |
| --- | --- | --- | --- |
| idle | 无选中 | 浏览/悬停/点击 | 选中 → selected |
| browsing | 指针进入手牌 | 悬停 peek、方向键、翻页 | 点击 → selected；离开 → idle |
| selected | 单击一张牌 | 查看动词条、拖出、右键菜单、Esc 取消 | 选动词 → targeting/amount；拖出 → dragging；Esc → idle |
| targeting | 选了需要目标的动词 | 高亮合法目标、径向选择、Esc 取消 | 选目标 → confirming/executing；Esc → selected |
| amount | 选了需要数量的动词 | 滑块/输入/快捷档、确认/取消 | 确认 → executing；取消 → selected |
| confirming | 不可逆/高代价动作 | 限时确认、取消 | 确认 → executing；超时/取消 → selected |
| dragging | 拖动超过 slop | 落点高亮、轮盘、松手/回弹 | 松手 → executing/selected；取消 → returning |
| executing | dispatch 中 | 等待结果；禁止重复提交 | 成功 → idle；失败 → selected + 错误提示 |
| prompt | 游戏提问 | 只能操作 prompt 选项 | 选择/超时 → idle |
| locked | 对手回合/结算/游戏结束 | 可查看，不可操作 | 轮到本人 → idle |

状态机的不变量：

- 一次手势只进入一个分支；不会同时「拖拽」和「长按执行」；
- 任何状态都有 Esc/取消路径（prompt 除外，除非规则允许放弃）；
- dispatch 前不产生状态变更；取消是干净的；
- 失败回显到卡片附近（shake + 原因），不只 toast。

### 7.3 指令轨交互

- 单击执行；不可用显示原因；
- 不可拖拽、不可长按菜单；
- 键盘：固定数字键 1–5，顺序与视觉一致；
- 破坏性指令（结束回合但还有行动点/可出牌）走限时确认条；
- 冷却/等待显示倒计时，不隐藏；
- 「更多」菜单里的指令不改变主轨槽位。

### 7.4 情境动词与目标选择

流程：

1. 选中对象 → 动词条出现（查看固定第一）；
2. 选动词 → 合法目标高亮；非法目标置灰 + 原因；
3. 目标选择：
   - 少量目标（≤8）：径向选择器 / 棋盘点击；
   - 大量目标：列表 + 搜索/分组；
   - 多选：显示 n/N，确认按钮；
4. 需要参数 → 数值面板；
5. 确认 → dispatch；取消 → 回到选中状态。

规则：

- 目标候选来自引擎 selection.candidates，UI 不造候选；
- 只有一个目标时，不逼玩家多点一次：动词直接执行或显示「对 X」确认；
- 目标名字不要进入手牌卡标题；目标只在选择器/提示中出现；
- 多目标（方天画戟、铁索）用「主目标 + 追加目标」两段式，不在手牌里裂成多张卡。

### 7.5 应答托盘交互

- 出现时自动聚焦第一个合法选项；不抢键盘输入框；
- 选项顺序固定：主要响应 → 次要响应 → 放弃；
- 倒计时显示在右侧；最后 3 秒变色；读屏每 5 秒播报一次，不每秒打断；
- 键盘 1–4；Enter 确认；Esc 仅在允许放弃时关闭；
- 多个 prompt 排队：显示 1/2；上一个结算后才显示下一个；
- 超时按游戏声明的 timeoutAction 执行；没有声明则保持等待，不自动替玩家做危险选择。

### 7.6 数值面板交互

- 滑块 + 数字输入双向同步；
- 快捷档（marks）来自游戏：底池、最小加注、全下、常用资源组合；
- 显示 min/max/step 和当前值；越界立即提示；
- 显示后果：支付后剩余、加注后筹码、弃牌后手牌数；
- 确认前不 dispatch；取消恢复原状；
- 移动端数字键盘弹出时，面板上移，避免遮住确认按钮。

### 7.7 取消、确认、撤销

| 场景 | 取消路径 | 确认策略 |
| --- | --- | --- |
| 选中卡 | Esc / 点空白 / 再点一次 | 无 |
| 目标选择 | Esc / 右键 / 轮盘外松手 | 单选直接提交；多选确认 |
| 数值输入 | 取消按钮 / Esc | 确认按钮 |
| 拖拽 | Esc / 松手空白 / pointercancel | 松手在出牌区 |
| 不可逆动作 | 确认条取消 | 5–8 秒限时确认 |
| 已 dispatch 的动作 | 不用 UI 撤销掩盖误点 | 引擎 rewind 是独立功能，不放日常操作 |

原则：**破坏性动作慢一拍，普通动作快一步**。不要给每个动作都加确认，也不要用 undo 代替清晰的确认。

### 7.8 手势冲突处理

- 手牌区禁止滚轮翻页（会与拖拽抢轴）；翻页用页码按钮/键盘；
- 指令轨不响应拖拽；
- prompt 打开时，手牌可查看但不可拖出；
- 拖拽期间禁用 OrbitControls（现有 scene.ts 已做）；
- 触屏长按 500ms 才开菜单；移动超过 14px 取消长按；
- 双击阈值 300ms；双击与单击的冲突用「第一次单击只选中，第二次在选中态才执行」消解。

## 8. 数据模型与契约改造

### 8.1 当前 UiAction 的问题

当前 UiAction（packages/app/src/contracts.ts:87–112）是一个扁平 DTO：

- group 同时承担「手牌分区」「排序」「上色」三种职责；
- entityId 既可能是手牌，也可能是市场卡、房间物品、装备；
- 没有 surface，UI 只能靠 entityId/fields/selection 猜；
- 没有 verb，动词只能从 actionType 字符串猜；
- 没有 prompt，响应和主动动作共用同一结构；
- id 是序号，不是身份；
- fields 里数字字段既可能是金额，也可能是选项，UI 用 kind === 'number' 猜「数值卡」。

### 8.2 建议的 DTO

~~~ts
export type UiSurface =

  | 'equip'     // 装备/持久/判定

  | 'reveal'    // 只读底牌/秘密
  | 'command'   // 回合指令轨
  | 'context'   // 情境动词
  | 'prompt'    // 应答/决策
  | 'amount';   // 数值/支付

export type UiVerb =
  | 'play' | 'equip' | 'use' | 'discard' | 'trade' | 'give'
  | 'build' | 'move' | 'attack' | 'explore' | 'pick'
  | 'respond' | 'pass' | 'end-turn' | 'roll' | 'draw' | 'ready'
  | 'choose' | 'confirm';
~~~

说明：

- UiAction 仍然是**一个可执行动作**，但它知道自己属于哪个面；
- UiHandCard 是**一个实体**，可以挂多个动词；手牌渲染实体，不渲染动作；
- UiPrompt 是**游戏提问**，选项是 UiAction，但 surface 固定 prompt；
- UiAmount 是数值面板的视图模型，不直接 dispatch，确认后把值合并回 UiAction。

### 8.3 分类算法（presenter 侧）

~~~ts
function classify(action, state, hints): UiSurface {
  // 1) 游戏可以显式声明（推荐用于少数例外）
  const declared = hints.actionView?.(action, state)?.surface;
  if (declared) return declared;

  // 2) 游戏在问：响应窗口 / 待提交决策 / 选择
  if (isPromptState(state, action)) return 'prompt';

  // 3) 实体：按 zone 决定
  const entity = action.entityId ? state.entities[action.entityId] : undefined;
  const zoneType = entity?.zoneId ? state.zones[entity.zoneId]?.type : undefined;
  if (zoneType === 'HAND') return 'hand';
  if (zoneType === 'EQUIP' || zoneType === 'TABLEAU' || zoneType === 'JUDGE') return 'equip';
  if (zoneType === 'BOARD' || zoneType === 'MARKET' || zoneType === 'DECK' || zoneType === 'DISCARD') {
    return 'context';
  }

  // 4) 棋盘目标
  if (action.targetNodeId || action.targetEdgeId) return 'context';

  // 5) 数值/支付
  if (action.fields?.some(isAmountField)) return 'amount';

  // 6) 无实体、无目标、无参数：回合指令
  if (!action.entityId && !action.selection && !action.fields?.length) return 'command';

  // 7) 其余：情境动词
  return 'context';
}
~~~

注意：

- isPromptState 不按游戏名判断，只看 state.interruptStack 顶部是否 WAITING_INPUT、是否有 pendingDecisions、是否有 pendingChoice；这些是内核通用结构。
- isAmountField 只看 widget === 'slider' 或 kind === 'number'，不猜语义。
- 游戏专用的「跟注也是 command」这类例外，由 actionView.surface 声明；不要写 if (gameId === 'poker')。

### 8.4 稳定 key 与签名

| 面 | DOM key | 签名变化 |
| --- | --- | --- |
| Hand | hand:{entityId} | 卡面、可打出状态、动词数量 |
| Equip | equip:{entityId} | 卡面、可用动词 |
| Command | cmd:{actionType} | 可用/禁用、冷却、标签 |
| Context | ctx:{sourceId}:{verb} | 目标数量、可用性 |
| Prompt | prompt:{promptId} | 选项、倒计时阶段 |
| Amount | amount:{actionId} | 数值、范围 |

CardHand.sync 只按这些 key 复用；快照刷新时同一实体不会重建。data-entity-id 是排错与探针的锚点。

### 8.5 游戏声明：actionView 进入 GamePresentationHints

建议在 packages/kernel/src/module.ts 的 GamePresentationHints 增加：

~~~ts
actionView?: (action: Action, state: ProjectedGameState) => {
  label: string;
  hint?: string;
  icon?: string;
  tone?: 'primary' | 'danger' | 'normal';
  surface?: UiSurface;
  verb?: UiVerb;
  slot?: number;
  risk?: UiRisk;
  confirm?: 'none' | 'timed' | 'modal';
} | null;
~~~

这样：

- 三国杀的「出【杀】」「发动【制衡】」留在 sanguosha/presentation.ts；
- 璀璨宝石的「捕捉宝可梦」留在 splendor/presentation.ts；
- 山屋的「破译神圣符文」留在 betrayal/presentation.ts；
- 通用层只保留中性默认：action.type → 可读标签、tone、icon；
- describeActionZh 的巨型 switch 可以退役，H9 解决。

### 8.6 GameSnapshot 的建议形态

~~~ts
interface GameSnapshot {
  // ...现有字段
  hand: UiHandCard[];        // zone HAND
  equip: UiHandCard[];       // zone EQUIP/TABLEAU/JUDGE
  reveal: UiHandCard[];      // zone REVEAL（只读）
  commands: UiAction[];      // surface='command'，按 slot 排序
  prompt?: UiPrompt;         // 当前活动 prompt
  amount?: UiAmount;         // 当前数值面板
  actions: UiAction[];       // 兼容/调试：完整动作表，不再直接进手牌
}
~~~

- actions 保留是为了旧 UI、AI 调试、探针和渐进迁移；新 UI 只读 hand/equip/reveal/commands/prompt/amount。
- hand 的顺序由 presenter 给出（默认排序），玩家手动排序存本地偏好；不把排序写回 GameState。
- equip 与 hand 分开，避免手牌翻页被装备挤占。

### 8.7 兼容与灰度

- 新字段全部 optional，旧客户端忽略；
- 新 UI 用 ?zones 开关，默认关闭；迁移完成后默认开启；
- 网络协议 additive：snapshot 多几个字段，不改 wire format；
- GameState 不变，回放哈希不变；
- AI 继续使用 engine.legalActions，不受 UI 分类影响；
- 旧 ?unified-hand 与新 ?zones 不叠加；迁移期只保留一个入口，避免三套 UI 同时渲染。

### 9.1 桌面布局

底部操作台从下到上：

| 应答托盘 | 56–72px | 仅当 prompt；覆盖指令轨，不遮手牌 |

CSS Grid 建议：

~~~
.dock {

  grid-template-areas:
    "prompt"

- 手牌区宽度 min(920px, calc(100vw - 2 * rail))；两侧留白保证不压角色卡/日志；

### 9.2 平板

- 手牌每页 5–7 张；
- 指令轨 4 条 + 更多；
- prompt 全宽，选项两列；
- 情境动词条从底部升起，不遮手牌。

### 9.3 手机

- 底部抽屉：默认只露资源条 + 手牌手柄；上滑展开手牌；
- 手牌每页 4–5 张，页码按钮；
- 指令轨 3 条 + 更多，固定在抽屉上方；
- prompt 覆盖抽屉上方，不遮手牌（玩家需要看牌回应）；
- 情境菜单用底部 sheet，不用悬浮小菜单；
- 所有触控目标 ≥ 44×44；env(safe-area-inset-bottom)；
- 长按 500ms 开菜单，移动 10px 取消。

### 9.4 可访问性

| 面 | role | 键盘 | 读屏 |
| --- | --- | --- | --- |
| 手牌 | listbox | Tab 进入；←/→；Enter 选择；Space 菜单 | aria-label = 牌名 + 类型 + 可打出/原因 |
| 指令轨 | toolbar | 1–5；Tab | aria-label = 指令 + 禁用原因 |
| 情境菜单 | menu | ↑/↓；Enter；Esc | 菜单项 = 动词 + 目标 |
| 应答托盘 | alertdialog | 1–4；Enter；Esc（允许时） | 标题 + 来源 + 选项 + 倒计时 |
| 数值面板 | dialog | Tab；↑/↓；Enter；Esc | 当前值/范围/单位 |
| 命令面板 | dialog + listbox | Ctrl+K；输入过滤；Enter | 全部可用动作的线性列表 |

补充：

- 倒计时不要每秒 aria-live；每 5 秒或最后 3 秒播报一次；
- 颜色不能单独承载信息：可打出/不可用同时用图标/文字；
- prefers-reduced-motion 下所有位移/弹簧压到 0.01ms；
- 焦点可见：focus-visible 外框至少 2px；
- 手牌翻页按钮有 aria-label 和页码 live region。

### 9.5 视觉语法

| 面 | 形状 | 目的 |
| --- | --- | --- |
| 手牌 | 矩形卡面（有图/有边框） | 「这是一张牌」 |
| 指令轨 | 圆角 pill / 按钮 | 「这是一个动作，不是牌」 |
| 情境动词 | 小 chip / 菜单项 | 「这是对当前对象做的事」 |
| 应答托盘 | 横幅 + 左侧色条 | 「游戏在问你」 |
| 数值面板 | 底部 sheet / 侧栏 | 「需要填一个数」 |
| 资源条 | 圆形/方形计数 chip | 「这是一个计数」 |

形状本身就是语义。不要把所有东西都做成卡，否则玩家无法区分「我拥有的」和「我能做的」。

### 9.6 性能

- 手牌只挂载当前页（4–9 张）；指令轨 ≤5；prompt 1 个；context 1 个；
- CardHand.sync 按稳定 key 复用；签名只包含卡面/状态，不包含 action id；
- 不在 rAF 内读布局（现有 cardHand.ts 的「帧内零布局读取」不变量继续遵守）；
- snapshot.actions 可以保留，但新 UI 不遍历它渲染；
- 大动作表（三国杀/山屋）不再生成等量 DOM，首屏渲染时间显著下降。

## 10. 竞技性与信息设计

### 10.1 四种辅助模式

| 模式 | 合法动作清单 | 提示 | 适用 |
| --- | --- | --- | --- |
| competitive 竞技 | 不显示 | 无 | 联机排位、正式对局 |
| standard 标准 | 不主动显示；选中后高亮合法目标 | 可选「提示」按钮，给 1 条建议 | 默认 |
| coach 教练 | 可展开侧栏清单 | 给 1 条建议 + 理由 | 新手/单人 |
| debug 调试 | 全量动作表 + 计数 | 无 | 开发/探针 |

实现上，snapshot.actions 始终存在；UI 是否渲染清单由模式决定。**不要在引擎层删合法动作**，否则 AI、回放、可访问性都会受影响。

### 10.2 显示「行动预算」，不显示「解法」

玩家需要知道：

- 还剩几点移动力/攻击次数/法力/筹码/资源；
- 当前阶段允许哪类动作（建造/交易/结束回合）；
- 哪些目标是合法的（选中动词后）。

玩家不需要默认看到：

- 「你可以对 A/B/C 分别使用 3 张牌」的完整笛卡尔积；
- 「最佳动作是 X」；
- 「胜率 62%」；
- 对手手牌的推断。

### 10.3 防泄漏

- 观战者：只看公开信息 + 「等待某玩家」；不显示 prompt 选项、不显示手牌；
- 热座/共享屏：prompt 出现时用「请把设备交给 X」遮罩；选项不提前显示；
- 直播：隐藏手牌区或使用延迟；动作清单不进入画面；
- 回放：只显示已公开的信息；prompt 选项在回放中不重建；
- 网络：snapshotFor(viewer) 已经按视角裁剪；UI 不缓存其他玩家的 hand/actions。

### 10.4 计时与确认

- 响应窗口倒计时由游戏声明；UI 只显示；
- 破坏性动作（全下、结束回合但还有行动、弃置关键牌）5–8 秒限时确认；
- 普通动作不确认；
- 不用「无限 undo」掩盖误点；引擎 rewind 是独立功能，放在菜单里；
- 超时代打按 timeoutAction，没有声明就等待，不替玩家做危险选择。

### 10.5 竞技模式的默认值

建议默认：

- 单击 = 选中，不是直接打出；
- 不显示合法动作清单；
- 不显示胜率/最佳动作；
- 目标高亮只在选中动词后出现；
- 手牌排序可手动覆盖；
- 结束回合固定最右；
- 响应托盘只列合法项 + 放弃。

单人/休闲可以放宽：单击直接出简单牌、显示提示、显示合法目标。

## 13. 开放问题与待裁定

1. **指令是否允许卡面皮肤？**
   建议不允许。指令用 pill/按钮；如果产品坚持卡牌视觉，也必须固定槽位、不可拖拽、不分页，且形状与手牌有明显差异。

2. **默认单击行为**
   建议竞技默认「单击选中 + 双击/拖出打出」；休闲可配置「单击直接打出」。需要产品拍板。

3. **真实行动牌游戏（Gloomhaven 类）**
   本方案支持：行动牌在 HAND，动词是「选择/打出/弃置」，不是把「移动 3/攻击 2」拆成命令卡。实现时用 zone=HAND + verbs，不需要游戏特判。

4. **多选目标 / 大量候选**
   径向选择器适合 ≤8 个目标；超过 8 个用列表 + 搜索/分组。多选显示 n/N，确认后提交。是否需要「全选」由游戏声明。

5. **同时决策 / 热座隐私**
   Prompt 托盘需要「遮罩 + 交接设备」模式；这属于响应层，不属于手牌。需要单独设计。

6. **无回合游戏**
   指令轨可以为空；只保留 prompt + transaction + resource。不要为了统一而强行造「结束回合」。

7. **观战/直播**
   观战不显示 prompt 选项和手牌；是否显示「合法动作数量」也要默认关闭。

8. **文案归属**
   actionView 进入 GamePresentationHints 后，describeActionZh 的迁移工作量较大；建议按游戏分 PR，先迁动作标签，再迁 surface/verb 声明。

9. **旧 ?unified-hand**
   与新 ?zones 的关系需要明确：迁移期只保留一个；最终删除旧 dock/hand-slot，不要长期双轨。

10. **动作表网络体积**
    当前 snapshot 仍带全量 actions；如果联机大局面出现 payload 压力，再考虑「按 surface 分片」或「客户端按需请求候选」。这属于后续优化，不影响本设计。

## 14. 附录

### 14.1 术语表

| 术语 | 含义 |
| --- | --- |
| 对象 / Entity | 游戏状态里有持久身份的东西：牌、装备、物品、棋子、房间、市场卡 |
| 动词 / Verb | 玩家对对象/局面施加的操作：打出、装备、使用、弃置、交易、建造、跟注 |
| 操作面 / Surface | 动词或对象出现的 UI 区域：手牌、装备、指令轨、情境、交易、应答 |
| 应答托盘 / Prompt | 游戏主动提问的阻塞式 UI，只列合法选项 |
| 情境动词 / Context | 绑定到当前选中对象/棋盘位置的动词 |
| 交易/数值 / Transaction | 需要金额、费用、支付、分配的面板 |
| 行动预算 / Action Budget | 玩家剩余的行动资源（移动力、攻击次数、法力、筹码等），不是合法动作列表 |
| 解法 / Solver | 把所有合法动作或最佳动作直接展示给玩家的辅助模式 |

### 14.2 当前字段到新字段的映射

| 当前 | 新 | 说明 |
| --- | --- | --- |
| UiAction.group = 'card' | surface = 'hand' + UiHandCard.zone | 按实体所在区域，不按动作形态 |
| UiAction.group = 'equip' | surface = 'equip' | 装备实体/槽位 |
| UiAction.group = 'skill' | surface = 'context'，source=角色/装备 | 技能是能力，不是手牌 |
| UiAction.group = 'command' | surface = 'command' / 'context' / 'prompt' / 'amount' | 按判定树拆开 |
| UiAction.entityId | source.kind='entity' + entityId | 只允许实体来源使用 |
| UiAction.fields 的数字 | surface='amount' + UiAmount | 数值面板，不是数值卡 |
| UiAction.selection | surface='context' + selection | 目标选择器 |
| UiAction.id = aN | hand:{entityId} / cmd:{type} / prompt:{id} | 稳定身份 |
| held display: | UiHandCard + zone=REVEAL/HAND | 同一实体，不再两套 id |

### 14.3 一页纸验收清单

- [ ] 手牌里没有「结束回合」「跟注」「建造」「出闪」这类无实体动作；
- [ ] 同一张牌在可打出/不可打出切换时，DOM key 不变；
- [ ] 手牌翻页只由牌数决定，指令不参与分页；
- [ ] 指令轨位置固定，≤5 条，溢出进「更多」；
- [ ] 选中一张牌才出现该牌的动词，不出现其他牌的动作；
- [ ] 响应窗口只列合法响应 + 放弃，不进入手牌；
- [ ] 数值动作确认前不 dispatch，取消可干净回退；
- [ ] 无手牌游戏不显示手牌区；
- [ ] 联机竞技默认不显示全量合法动作；
- [ ] 键盘/读屏可以完成「选牌 → 选动词 → 选目标 → 确认」全流程；
- [ ] 任何失败都有就近的人话原因，不只 toast；
- [ ] verify:all 全绿。
